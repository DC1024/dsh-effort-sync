缺口只有一环，但正好卡在最后一格

不是供应商没报，也不是 DSH 没有概念——是发现契约里没有放它的地方。

01

发现契约没有 reasoning 槽位

LlmDiscoveredModel = { id, name?, contextWindow?, maxTokens?, inputModalities? } ——即使供应商在 /v1/models 里报了能力，DSH 也搬不进来。

02

能力只有一条入口

LlmResolvedModelInfo.reasoning 来自适配器自报或目录声明（reasoningEfforts）， 而网关通常不替每个模型写声明。

03

于是选择器空着

像 magpie 这样已经提供 supported_reasoning_levels 的网关， 新加的模型依旧没有任何档位可选——只能手写 YAML。

TOOL sync_reasoning_levels

给 agent 的干跑工具

默认 dryRun: true，只报告差异；要落地就显式 dryRun=false。 参数还有 provider / only / noneMapsToOff / replace。

provider限定某个供应商（默认全部声明的）
dryRun默认 true，只报告不写
only只同步指定模型 id
noneMapsToOff是否把上游的 none 映射成 off（默认不猜）
replace用上游列表替换声明（默认加性合并）
// EVIDENCE

差别长这样

没有魔法，就是一次集合补齐：保留你已有的映射，加入上游公布的档位，DSH 不认识的值只报告。

模型之前之后备注
group/smart-split （无声明） low · high 上游只报两档，就只补两档
cc/gpt-6-luna max （wire: ultra） low · medium · high · xhigh · max 已有拼写保留，缺的补上
cc/deepseek/…-flash （无声明） off · low · medium · high · xhigh · max 含 off：可显式关掉思考
never-advertised （无声明） 原样不动 上游没广告的模型不猜
上游的 none — 跳过并提示 是否映射成 off 由你决定

实测（本机 magpie）：上游 103 个模型，目录里 4 个；供应商报的档位常是上游能力的 保守子集——所以默认只增不减，replace 要显式开启。

// DESIGNED TO NOT SURPRISE YOU

安全设计

写配置这件事，宁可啰嗦一点。

  • 默认不写：工具 dry-run 先行；按钮是显式点击，写完把差异回报给你。
  • 只写 DSH 认识的档：词表固定 off / minimal / low / medium / high / xhigh / max。
  • 保留既有 wire 拼写：max: ultra 这类的映射不会被覆盖。
  • 加性优先：只增不减，掉档位这种不可逆动作必须显式 replace。
  • 不动上游没广告的模型：查不到就原样跳过，并在报告里说明。
  • 不碰凭据：只经 credentials.resolve(apiKeyEnv) 取值，不落盘、不打印。
  • 不整块改写供应商：只写 models，并按字段把下层已有的密钥/地址补全，不会写空。
  • 单点故障不扩散：某个供应商读不通，只单独报告，不阻断其它写入。
已知边界

上游标 reasoning: false 的模型，插件不会替你写 reasoningEfforts: false（那会让选择器消失，属于行为变更）——只在报告里提示你手工决定。
